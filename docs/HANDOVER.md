## 1. 任务与唯一指标

**做什么**:AI 图生视频产出的卡通 IP「蘑菇 TUTU」约 5 秒短视频,做 badcase 复核漏斗判别器。
人工复核成本高,希望模型先把明显没问题的放行,把可疑的留给人看。

**唯一指标**:`gn@95` / `ev@95` —— **在 95% bad 召回的阈值下,可放行样本(good+normal)被放行的比例**。
- 阈值 T 定义:把所有 bad 的预测分数排序,取第 5% 分位(即允许 5% 的 bad 漏过)
- 分子:分数低于 T 的 good+normal 数量;分母:全部 good+normal
- 代码里长这样(所有脚本统一):
```python
def gn(p, y, rec=0.95):
    b = np.sort(p[y == 1])
    T = b[len(b) - int(np.ceil(rec * len(b)))]
    return float((p[y == 0] < T).mean())
```
- 辅助口径:`ev@90`(放宽到 90% 召回)、`ev@100`(零漏检)、AUC

**为什么是这个指标**:业务上漏检代价远高于误拦,所以召回率固定,优化放行率。

```python
import boto3, json
from botocore.config import Config
s3 = boto3.client('s3', region_name='us-east-2', config=Config(signature_version='s3v4'))
out = []
for name in ('train_v3', 'eval_v3'):
    for l in open(f'splits/{name}.jsonl'):
        rel = json.loads(l)['abs_path'].split('data/s3/', 1)[1]   # abs_path 里就有 S3 相对路径
        url = s3.generate_presigned_url('get_object',
              Params={'Bucket': 'trash-in-picaa', 'Key': 'Datasets/tutu-video-eval/' + rel},
              ExpiresIn=28800)
        out.append(rel + '\t' + url)
open('dl_all.tsv', 'w').write('\n'.join(out))
```

### 实验纪律(这是这个项目的核心资产,别跳过)
1. **预注册**:每个实验发车前,先把假设、变体、**判准**写进 `data/prod500/FACTOR_PREREG.md`,
   然后再看结果。这份文件是判决账本,1000+ 行,记录了每一条已探索路径的结论。
2. **判准发车前冻结**,不能看到结果再调。
3. **train-OOF 门禁**:任何改动必须先在 train-OOF 上超过 **0.3218**,才有资格碰 eval。
4. **eval 单发纪律**:eval_v3 是最终评估集,每次接触都要记账(**已用 10 次**)。

5. **判准要写成区间比较,不是点比较** —— 这是被坑两次后的教训:
   - ❌ `真值 > 对照均值` / `点估计 > 0.55`
   - ✅ `真值 > 对照分布上沿` / `95%CI 下界 > 随机基线`
6. **对照要能证伪**:置换检验、随机分组对照、纯噪声列。
   已知这个组合器**加一列纯噪声就能 +1.8pt**(0.2461 → 0.2643),
   所以任何"加专家列"的实验都必须先扣掉这个方差红利再谈增益。

**关于 32B 那个 0.5727 —— 值得单独讲,因为它是最有教育意义的假阳性**:
- fold0 tail-AUC 0.5727,95%CI [0.524, 0.621],**下界 > 0.5,统计上显著**
- 满折跑完 0.5316,95%CI [0.497, 0.566],**包含 0.5,不显著**
- 由满折反推 fold1 ≈ **0.4889**,两折差 0.084 = 单折标准误的 **3.4 倍**
- 教训:判准 `点估计 > 0.55` 在 n_tail=163 时根本区分不开随机(0.55 的 CI 是 [0.502, 0.598])。
  **应该写成 `CI 下界 > 0.5`**

**tail-AUC 是什么**(自定义诊断指标,你可以质疑它):
取 E18 train-OOF 分数最低的 20% bad(即顶住阈值、决定放行率的那批,记 tailB),
对全部可放行样本算 AUC。动机是:整体 AUC 不作数——E34 的 0.665、E36 的 0.649 都不差,
入栈后无一过 0.3218,所以需要一个直接测"有没有看见尾部"的指标。

### 5.4 规则线(可解释检测器)

用"传统特征预筛 + VLM 客观事实提问 + 盲样对照"做了几个单缺陷检测器:
- **眉毛检测**(官方设定无眉毛,长出眉毛即 bad):精度 **81–84%**,蒸馏 CNN 甚至抓到过教师漏的案例
- **悬空检测**:31 条确认,盲测误报 3%
- **场景跳变**:精度 64%,盲测误报 2%
- **尾巴粉色物体**:63 个候选

**但 2026-08-09 查清了一件事**:眉毛 v6 在 eval 命中 35 条(29 bad / 5 normal / 1 good),
**这 29 条 bad 的模型分数中位 0.685,而阈值只有 0.226 —— 模型本来就全拦下了**;
与顶阈值的 20 条 tail bad 交集 = **0**,与 top60 交集 = 1。

→ **规则线是可解释性资产(给人一个能核对的理由),不是放行率资产。**
→ 局限:这个结论是在"作为独立门禁"的口径下算的。**如果业务上需要"给出拦截理由",规则线仍然有价值。**

**Prompt 工程的三条经验**(做 VLM 事实提取时反复验证):
1. **分辨率是召回杠杆** —— 局部 zoom 找回了此前全部漏检的眉毛
2. **诱导性提问会造成假确认** —— 负对照组也会说"是",必须设盲样
3. **排除条款必须增量添加** —— 重写判断框架会让崩溃方向翻转

## 6. 关键的量化事实:战场只有 20 条视频

这是 2026-08-09 才算清楚的,**建议接手后第一件事就是理解这个**:

eval 阈值 T = 0.2259,由**分数最低的 20 条 bad** 顶住。修好它们的边际收益:

| 修好最低 k 条 bad | 阈值 T | 放行率 |
|---|---|---|
| 0(现状) | 0.2259 | **29.13%** |
| 5 | 0.2545 | 33.75% |
| 10 | 0.2708 | 37.48% |
| 20 | 0.2985 | 43.34% |

**每修好一条 tail bad ≈ +0.9 个百分点。** 这解释了为什么 E32/E38–E43 那一长串实验全部归零——
它们改的都是全局排序,一条都没碰这 20 条。

这 20 条的 E18 分数是 0.039~0.224,**低于 good 的中位数 0.304** —— 模型认为它们比一半可放行的视频还干净。

清单(eval_v3):
```
16955 16713 15028 5719 15051 15043 6565 16408 15720 15205
6036 15777 6000 16610 15609 17148 5822 16677 6228 16396
```
(`5822.mp4` 是曹源指认过的尾巴缺陷锚样本)

**分档分数分布**(eval,E18):
| 档 | n | p10 | p25 | **p50** | p75 | p90 |
|---|---|---|---|---|---|---|
| good | 325 | 0.047 | 0.126 | **0.304** | 0.449 | 0.610 |
| normal | 238 | 0.171 | 0.258 | **0.378** | 0.511 | 0.632 |
| bad | 405 | 0.299 | 0.388 | **0.555** | 0.685 | 0.789 |

模型在从未见过 normal 标签的情况下,自发学出了 good < normal < bad 的序。

## 7. 未解疑点 / 开放线索

1. **crops_v3 覆盖率的不对称,至今没有解释**:
   train 有 1028 条(26.5%)没有 SAM3 裁剪,其中 **999 条是 bad**(占全部 bad 的 61.6%);
   而 eval 只缺 14 条(1.4%)。如果是"bad 视频角色异常导致检测失败",eval 的 405 条 bad 不该几乎不缺。
   **更像是 train 侧提取没做完。** 这件事本身可能藏着信息(能不能提取出角色 = 一个强 bad 信号?),
   但要小心它是捷径:曾经因为这个做出过 AUC 0.8227 的假结果。

2. **好样本侧的标签交叉检验从没做过**:把眉毛/悬空/僵硬检测器的高分命中与 eval 的 563 条可放行样本取交集,
   找可能被误标的 good。零成本,本地就能跑。

3. **i2v 首帧原图**:历史上被列为"头号数据请求"至今没拿到。
   唯一的强轴 `c_first_last` 就是自参照的旁证 —— 如果能拿到生成端的首帧原图,
   还原度类缺陷可能有完全不同的解法。

4. **生成端元数据**(prompt / seed / 模型版本 / 采样参数):从没要过。

5. **合成缺陷监督**(在好帧上人工贴黑点/扭嘴/加肢体,冻结骨干训轻头,晋级关用真实 bad):
   历史上被标记为"唯一未测范式",至今未做。

6. **人工审核过的事实**:曹源审了 103 条最难的 bad,判断"最多 5 条可以接受"
   → bad 侧标签噪声 ≤5%,**29.1% 是真实的模型边界,不是标签噪声造成的**。
   他给的缺陷主诉是:僵硬/不柔软/刚体式运动/没有生命力,以及还原度(嘴巴、眉毛、尾巴)。

## 8. 工程上踩过的坑(直接抄,别重踩)

1. **`pgrep`/`pkill -f` 自匹配**:`pkill -9 -f e45_vlm_tri` 会杀掉自己所在的 ssh 会话
   (它的 cmdline 里含这个字符串)。用方括号写法 `[e]45_vlm_tri`,或用 pidfile/marker 文件。
2. **别在 ssh 命令串里拼 shell 脚本**:多层转义会把 `"$@"` 写成字面量,导致所有实验启动瞬间秒退,
   而接力脚本还在傻等一个永不出现的结束标记(看起来像"在跑")。
   **正确做法:本地 Write 出文件 → scp → ssh 只执行一句 `setsid nohup bash /root/x.sh &`。**
3. **远程任务"在不在跑"要以 `nvidia-smi` 显存/利用率或日志进度行为准**,不能以"接力脚本还活着"为准。
4. **并行实验的显存**:上一批崩掉的进程可能不释放显存(见过残留 44GB 把下一批全 OOM 掉)。
   接力脚本发车前必须等 `nvidia-smi --query-compute-apps=pid --format=csv,noheader` 返回空。
5. **并行 cv2 必须限制 ffmpeg 线程**:`OPENCV_FFMPEG_CAPTURE_OPTIONS=threads;1` +
   `cv2.setNumThreads(1)` + workers ≤16。曾因 48 worker 耗尽 ffmpeg 线程出过事故。
6. **VLM 微调慢的第一嫌疑人不是 GPU**:判据是 GPU 利用率 0% 而 load average 高 → CPU 预处理瓶颈。
   实测三处改动累计 **27 倍**提速(7.8 s/样本 → 0.29 s/样本):
   - 8B 别用 4bit(bf16 只要 16GB,H100 放得下,nf4 反量化慢 2-3 倍)
   - DataLoader `num_workers=16~24` + `prefetch_factor=6`(收益最大)
   - 两个实验并行把 GPU 利用率从 60% 推到 100%
   注意:worker 靠 fork 继承内存,Dataset 类和 collate_fn 必须是**模块级**(lambda 不可 pickle)。
7. **预量化仓库与 bitsandbytes 版本**:`unsloth/*-bnb-4bit` 与 bitsandbytes 0.50.0 不兼容
   (`fix_4bit_weight_quant_state_from_module` 断言失败)。用官方权重 + 运行时 nf4 量化。
8. **离散/并列分数算 AUC 必须用 midrank**(`scipy.stats.rankdata`),否则会出伪影。

## 9. 给下一步的开放建议

**我的判断可能是错的,以下只是线索,不是结论。**

已经确认收益最大的方向不在模型侧:

- **业务侧**:召回口径从 95% 放宽到 90%,29.1% → **43.3%**,零成本。这是目前性价比最高的一张牌。
- **看那 20 条**:第 6 节的清单。曹源对它们共同点的判断,信息量可能大于再堆十个训练变体。
  做 gallery 给他看是个具体动作。
- **数据侧**:产线域标注量历史上被测算为真正的瓶颈(prod500 只有 27 条 bad,
  即便全抓,漏检率 95% 上界仍有 12.5%;认证 <1% 需要约 300 条 bad)。

模型侧还没被排除干净的:

- **E46 尾部专训**的思路(只在最差样本上训练)**没被证伪,只是被样本量卡死**。
  冻结更多层、只训轻量头、或放宽 tail-frac 到 40-50%,都可能让它活过来。
- **E49 的"整帧 + 672px"**从没跑过,是分离"覆盖率"与"分辨率"两个因素的干净方法。
- **E34 的骨干只试了两个**(effb0 0.665 / convnext 0.507),更强的视频骨干没试过。
- **给模型看它现在看不到的东西**:比如用 RAFT 算光流、把光流场渲染成图和原帧一起喂进去,
  让"刚体式运动"在视觉上直接显形(刚体运动光流场均匀,自然运动有结构)。
  这条设计过但没执行,因为 16 帧实验先失败了 —— 但那个失败不足以否定它。
- **合成缺陷监督**(第 7 节第 5 条),历史上标记为唯一未测范式。

**最后提醒**:这个项目最大的风险不是找不到提升,是**找到假的提升**。
2026-08-09 一天之内出现过三个"看起来成功了"的结果,全部被自己的对照实验否掉:
32B 单折 0.5727(满折掉回)、入栈 +5.61pt(置换检验证伪)、补数据后 AUC 0.8227
(整帧/裁剪的呈现方式捷径)。任何一次没查,就会带着假提升去汇报。

**判准写成区间比较、对照要能证伪、train 过门才碰 eval —— 这三条是这个项目最值钱的东西。**
